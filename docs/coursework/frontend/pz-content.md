# ВВЕДЕНИЕ

В курсовом проекте я разработал пользовательский интерфейс KeyCraft AI для подбора механической клавиатуры из реальных товаров. Пользователь выбирает основу, свитчи и кейкапы, получает расчёт целых упаковок, сохраняет список и открывает карточку продавца. Для реализации использованы Next.js, React Context API, Tailwind CSS и GSAP. Работа выполнена от лица Алимканова Жасулана, группа ИС-24-22б, по дисциплине «Основы frontend».

Покупка механической клавиатуры по частям требует сопоставить раскладку, посадочные места, количество свитчей и комплектность основы. При выборе barebones корпуса с платой легко повторно включить уже установленные стабилизаторы или заказать недостаточно свитчей. Ещё одна практическая проблема — разрозненные карточки магазинов: название модели, цена упаковки и цена одной детали имеют разный смысл. Интерфейс должен показывать состав покупки понятным языком и сохранять проверяемую связь с конкретным товаром.

Цель работы — создать адаптивный frontend, который объединяет публичный сайт, личные списки покупок и административное SPA с настоящим Laravel API. Основной результат — работающий локальный продукт с реальными предложениями магазинов Казахстана и материалами для его воспроизводимого запуска и демонстрации.

Для достижения цели я выделил задачи: изучить итоговое задание Frontend; спроектировать страницы и состояние; создать адаптивную тему; подключить авторизацию и CRUD; реализовать расчёт розничной сборки; добавить GSAP и ИИ-помощника; проверить сценарии и оформить документацию. Объект работы — процесс выбора комплектующих механической клавиатуры. Предмет работы — страницы, формы, клиентское состояние и взаимодействие интерфейса с программным API.

Готовый backend по исходному распределению работ разработан Нукушевым Чингизом. В моей работе он используется как существующая серверная система. Для нового сценария добавлены каталог розничных предложений, расчёт упаковок и сохранение shopping_plan. Эти интеграционные изменения описаны отдельно от первоначальной аутентификации, складских заказов и модели данных Backend.

Основание работы — итоговое задание курса «Основы frontend»: framework Next.js или Nuxt, менеджер состояния, CSS framework и пять разделов администрирования. Записка содержит три главы, заключение, источники и приложения.

# 1 АНАЛИЗ ЗАДАЧИ И ТРЕБОВАНИЙ

## 1.1 Предметная область и сценарий покупки

Механическая клавиатура состоит из корпуса, печатной платы, монтажной пластины, стабилизаторов, свитчей и колпачков клавиш. Однако ассортимент реального магазина может продаваться комплектами. Поэтому количество сущностей внутреннего каталога нельзя автоматически переносить в покупательский список. В проекте основой выбран Glorious GMMK PRO Black Slate ANSI: barebones уже включает корпус, плату, плейт и установленные стабилизаторы. Пользователю остаётся добавить свитчи и кейкапы [6, 7].

Для ANSI версии рассматриваемой основы требуется 82 свитча. Наличие поворотного регулятора не добавляет ещё один свитч. От ISO варианта, где меняется раскладка и число позиций, проект намеренно отказывается: сведения о совместимости относятся к конкретному ANSI комплекту. Проверка не распространяется на любую клавиатуру с надписью 75 процентов.

Пользовательский путь начинается с главной страницы, продолжается каталогом или конструктором и заканчивается прямой ссылкой на конкретную карточку продавца. Сохранённая сборка представляет список покупок, а не оплату, резерв или доставку. Суммы взяты из проверенного снимка карточек. Магазин подтверждает наличие в выбранном городе и окончательную цену при оформлении.

Я использовал предложения Белого Ветра, Vendara и Over-Shop. Для одного товара допускаются несколько продавцов: Gateron Red присутствует в двух предложениях, но по снимку доступен только у Vendara. Поэтому выбор предложения сначала учитывает доступность, затем цену. Более низкая цена отсутствующего товара не должна подменять доступный вариант.

Таблица 1 — Сравнение способов подбора

| Способ | Преимущество | Ограничение |
|---|---|---|
| Карточка одного магазина | Можно сразу оформить покупку у продавца | Пользователь самостоятельно связывает несколько товаров |
| Список ссылок в заметках | Не требует регистрации | Нет расчёта упаковок и проверки категорий |
| KeyCraft AI | Связанный список, расчёт, сохранение, ИИ-подбор | Каталог ограничен проверенными моделями, оплата у продавца |

## 1.2 Требования курса и границы реализации

В качестве основного framework я выбрал Next.js с App Router, поскольку он позволяет описывать маршруты файлами и объединять страницы общим layout. Менеджер состояния реализован средствами React Context API и useReducer. Tailwind CSS подключён через PostCSS и применяется для сеток, форм, состояний загрузки и отдельных элементов. Дополнительно создана собственная тема в светлых и оливковых оттенках [1–3].

Публичная часть содержит главную страницу, каталог и описание работы сервиса. На всех страницах есть единая навигация. Конструктор, авторизация, личный кабинет и ИИ-подбор расширяют этот минимум. Административное SPA состоит из обзора, комплектующих, предложений, заказов и пользователей.

Реальные предложения и учебный склад разделены по смыслу. Публичный каталог читает resources/data/retail-catalog.json. Административная панель управляет существующими таблицами Laravel с учебными компонентами, предложениями и складскими заказами. Заказы в Белом Ветре не отображаются как созданные заказы KeyCraft: у проекта нет договорённой интеграции оформления с этим продавцом.

Такое разделение позволяет использовать готовый backend без вымышленных закупок. Одна сохранённая сборка либо содержит прежние складские items, либо новый shopping_plan. Сервер блокирует смешивание с ответом 409. Этот контроль предотвращает ситуацию, когда цена розничного списка ошибочно списывает внутренний остаток.

## 1.3 Пользователи и права доступа

В системе предусмотрены гость, покупатель и администратор. Гость может изучить каталог, открыть карточку и составить локальный черновик. Покупатель после входа сохраняет и редактирует свои списки, удаляет их и использует ИИ-подбор. Администратор получает панель управления учебным складом. Значение роли, переданное формой регистрации, не принимается сервером.

Таблица 3 — Матрица доступа

| Действие | Гость | Покупатель | Администратор |
|---|---|---|---|
| Просмотр реального каталога | Да | Да | Да |
| Локальный черновик | Да | Да | Да |
| Личные списки и ИИ | Нет | Только свои | Нет |
| CRUD складского каталога | Нет | Нет | Да |
| Все складские заказы | Нет | Только свои через API | Да |
| Роли пользователей | Нет | Нет | Да с серверными ограничениями |

Скрытие ссылки в меню улучшает навигацию, но не является защитой. Компонент Guard проверяет состояние пользователя до показа закрытой страницы, а Laravel policy и middleware повторно проверяют роль и владельца каждого ресурса. Поэтому запрос к чужому ID не становится допустимым после ручного изменения URL.

Авторизация использует токен Sanctum, который возвращается при входе и передаётся в заголовке Authorization. Токен хранится в sessionStorage и не включается в публичные запросы каталога. При ответе 401 HTTP-модуль удаляет токен и уведомляет Context. Черновик хранится отдельно и остаётся доступным после окончания сессии.

## 1.4 Дизайн и информационная архитектура

Основная визуальная идея — показать клавиатуру как набор управляемых деталей. Светлый фон, тёмно-зелёный текст и лимонный акцент выделяют основной переход в конструктор. Шрифт Manrope хранится локально с лицензией OFL, поэтому отображение не зависит от обращения к Google Fonts во время работы приложения.

Главная страница содержит заголовок, короткое описание, интерактивную схему и переходы к товарам. Каталог показывает фотографию, название, категорию, цену упаковки или комплекта и дату проверки предложения. Для случая отсутствия товара предусмотрена отдельная формулировка и ссылка на карточку, без обещания немедленной покупки.

# 2 ПРОЕКТИРОВАНИЕ FRONTEND И ИНТЕГРАЦИИ

## 2.1 Маршруты и компоненты

Приложение размещено в отдельной папке frontend. Laravel остаётся API сервером на 127.0.0.1:8120, а Next.js обслуживает интерфейс на localhost:5173. Разные origin согласованы через FRONTEND_URL в серверном окружении. Публичная переменная NEXT_PUBLIC_API_BASE_URL содержит только адрес API; ключи провайдеров в неё не помещаются.

Таблица 4 — Основные маршруты

| Маршрут | Компонент или страница | Доступ |
|---|---|---|
| / | Hero и карточки | Все |
| /catalog | Поиск и предложения | Все |
| /guide | Четыре шага подбора | Все |
| /builder | Конструктор и расчёт | Черновик для всех |
| /login и /register | Формы авторизации | Все |
| /account/builds | Сохранённые списки | Покупатель |
| /ai | Языковая модель | Покупатель |
| /admin и вложенные разделы | AdminContent | Администратор |

Общий layout включает StoreProvider и оболочку Shell. В components выделены продукты, формы, модальные окна, конструктор, административные операции и GSAP. В lib находятся типы и единый HTTP-клиент. Такое разделение позволяет менять оформление карточки, не дублируя механизм передачи токена и обработки ошибок.

Файловые маршруты Next.js заменяют ручной разбор location.hash прежнего демонстрационного клиента Backend. Между страницами используются Link и клиентские переходы. Административный маршрут содержит необязательный сегмент section, который выбирает одно из пяти представлений. При смене раздела закрываются формы редактирования и карточка заказа.

Прежняя папка client сохранена как архив демонстрации Backend. Основной запускаемый продукт и требования Frontend относятся к папке frontend. Это явно обозначено в README и скрипте запуска, чтобы при проверке не открыть старую версию.

## 2.2 Состояние и сохранение данных

В StoreProvider используются Context и reducer. В общем состоянии находятся user, authLoading, draft, draftReady, products и notice. Reducer описывает смену пользователя, обновление черновика, завершение загрузки, каталог и уведомления. Дочерние страницы получают состояние через useStore, не передавая токен через цепочку свойств [2].

Таблица 5 — Размещение состояния

| Данные | Хранилище | Причина |
|---|---|---|
| Текущий пользователь | Context после auth/me | Единая навигация и права |
| Bearer token | sessionStorage | Сессия вкладки, удаление при выходе |
| Несохранённый выбор | Context и localStorage | Восстановление после перезагрузки |
| Сохранённая сборка | MySQL builds.shopping_plan | Доступ по аккаунту и проверка владельца |
| Цена и наличие | Серверный снимок каталога | Клиент не задаёт стоимость |
| Поиск и фильтры | Состояние страницы каталога | Не смешиваются с авторизацией |

Черновик включает kit_id, switch_id, keycap_id, name и budget. После сохранения добавляются buildId и ownerId. Если входит другой пользователь, привязка к прежней сохранённой сборке удаляется из черновика. При этом выбранные товары могут остаться локальной идеей, которую новый владелец сохранит отдельно.

При открытии /builder?id=... сначала показывается загрузка, затем данные проверенной сервером сборки. Это важно для предотвращения гонки: пользователь не должен изменить старый локальный черновик в момент, когда ответ API ещё загружает другой список. При отказе показывается сообщение и переход к своим сборкам.

Изменение выбора запускает пересчёт. Ответ предыдущего запроса игнорируется, если за это время выбран другой товар. Пока расчёт не завершён, кнопка сохранения недоступна. Название и бюджет не вызывают повторный расчёт состава, поскольку он зависит от трёх ID.

## 2.3 Контракт API и ошибки

HTTP-модуль передаёт JSON, заголовок Accept и токен для закрытых операций. cookies не используются: credentials задан как omit. Таймаут запроса составляет 45 секунд. API возвращает ошибки в общем формате message/errors; клиент сохраняет request ID из заголовка для диагностики и выводит понятный текст.

Таблица 6 — Новые операции интеграции

| Метод и путь после /api/v1 | Назначение | Доступ |
|---|---|---|
| GET retail/products | Каталог предложений | Публичный |
| POST retail/quote | Расчёт по трём ID | Публичный |
| GET builds/{build}/shopping-plan | Пересчёт сохранённого списка | Владелец |
| PUT builds/{build}/shopping-plan | Сохранение выбора | Владелец |
| POST retail/recommendations | ИИ подбор из каталога | Покупатель |

Вместе с существующим backend контракт содержит 44 операции. Переносимая коллекция Postman и OpenAPI генерируются из одного файла документации. Дополнительная проверка сравнивает документированные методы с artisan route:list и проверяет ссылки схем. Документация доступна локально на /docs; её публичная публикация не выполнялась.

Ответ 401 очищает состояние авторизации. Ответ 422 сохраняет ошибки конкретных полей и введённые данные. Ответ 403 объясняет отсутствие прав, 404 — отсутствие ресурса, 409 — конфликт сценариев. При 503 от ИИ пользователь может повторить подбор или самостоятельно выбрать детали. Ошибка внешнего сервиса не должна очищать черновик.

Формы на стороне клиента проверяют обязательность, длину, диапазоны и формат JSON характеристик. Сервер повторяет проверку, поскольку браузерные ограничения можно обойти. В розничном расчёте поля price, total и user_id запрещены: сумма строится только из серверных предложений. Публичный запрос каталога не передаёт сохранённый токен без необходимости.

## 2.4 Реальный каталог и алгоритм расчёта

Каталог содержит 5 основ, 8 вариантов свитчей и 7 наборов кейкапов: всего 20 моделей и 27 предложений. У каждой записи есть стабильный строковый ID, категория, фотография, комплектность и предложения с merchant, HTTPS URL, ценой, наличием и checked_at. Это проверенный вручную снимок, а не непрерывный парсер. Через семь дней сервер выставляет признак stale и добавляет предупреждение.

Базовая совместимость подтверждает сочетание выбранной ANSI основы GMMK PRO или GMMK 2, механических MX свитчей и покрытия раскладки кейкапами. Для GMMK 2 используются 67 или 99 позиций, для GMMK PRO —82. Наборы Razer, HyperX и Aura без подтверждённого покрытия нестандартных клавиш отображаются с предупреждением; их совместимость автоматически не утверждается. Проект не обещает одинаковый звук во всех условиях: он зависит от корпуса, установки и модификаций. Доставка, итоговые скидки, гарантийные условия и наличие в городе не входят в сумму снимка.

Для Gateron Red достаточно одной упаковки на 120 штук. Запас составляет 38 свитчей. Итоговая сумма проверенной сборки —70 845 +20 613 +29 990 =121 448 ₸. Для GMMK 2 на 67 клавиш нужны 2 упаковки HyperX по 45 штук; с Black Ash итог равен 78 717 ₸. На 99 клавиш нужны 3 упаковки; итог — 85 274 ₸. Внутри API суммы хранятся целыми тиынами.



# 3 РЕАЛИЗАЦИЯ И ПРОВЕРКА ПРОДУКТА

## 3.1 Каталог и конструктор

Каталог поддерживает поиск по названию, бренду и описанию, фильтр категории, магазина и наличия, сортировку по цене или имени. useDeferredValue отделяет ввод строки от обновления результатов. Фильтры работают по загруженному небольшому набору; сервер также поддерживает отдельные параметры для внешних клиентов. На странице выводится до шести моделей.

Если поиск не дал результатов, карточки заменяются объяснением с предложением изменить фильтры. Ошибка загрузки содержит кнопку повтора. При первом обращении отображается skeleton. Из карточки можно открыть модальное окно с характеристиками и всеми предложениями либо сразу добавить позицию в конструктор.

[FIGURE catalog-desktop.jpg | Рисунок 2 — Каталог с фильтрами и товарными фотографиями]

Конструктор содержит три списка выбора, название, бюджет и итоговую область. Бюджет показан в тенге, но перед сохранением преобразуется в тиыны. Сумма выше бюджета выделяется предупреждением. Неполный список разрешён как черновик; интерфейс не изображает такую подборку полностью совместимой.

Сохранение выполняется последовательно: при необходимости создаётся собственная Build, затем PUT shopping-plan записывает выбор. Полученный ID сохраняется сразу, поэтому повтор после сетевого сбоя не создаёт лишнюю сборку при повторном нажатии в той же сессии. Список доступен в личном кабинете; изменение имени и бюджета выполняется через PATCH, состава — через PUT.

[FIGURE builder-packs.jpg | Рисунок 3 — Фрагмент конструктора с расчётом трёх упаковок Lynx]

Удаление собственной сборки и складской записи требует отдельного окна подтверждения. Во время проверки браузера я проверил отмену удаления, не подтверждая необратимую операцию над существующими записями. Удаление и защита владельца дополнительно покрыты серверными тестами на изолированной тестовой БД.

## 3.2 Анимация GSAP и адаптивность

Для анимации применены официальные материалы greensock/gsap-skills и библиотека GSAP 3.15.0 с @gsap/react2.1.2. useGSAP ограничивает селекторы контейнером ref и очищает созданные анимации после размонтирования. Обработчик кнопки разбора клавиатуры обёрнут в contextSafe, чтобы создаваемая по нажатию timeline также принадлежала контексту [4, 5].

На главной текст появляется с небольшим сдвигом, а клавиши — последовательно от центра. Схема клавиатуры создана средствами HTML и CSS, не является фотографией реального изделия. Кнопка меняет расстояние между корпусом, платой, плейтом и кейкапами. Параллакс указателя работает только при pointer:fine и достаточной ширине экрана.

Карточки и информационные блоки появляются через ScrollTrigger. Используются transform и autoAlpha; изображения после загрузки обновляют измерения триггеров. Очистка удаляет обработчики изображений и pointer events. При prefers-reduced-motion входные эффекты и анимация прокрутки отключаются, а разбор выполняется без продолжительного движения.

Адаптивные правила перестраивают главную и конструктор в одну колонку, уменьшают декоративную клавиатуру и переносят навигацию. Таблицы администрирования сохраняют читаемые столбцы и прокручиваются внутри собственного контейнера. Избыточная область 3D проекции на телефоне ограничена сценой, чтобы не создавать горизонтальную прокрутку всей страницы.

[FIGURE home-mobile.jpg | Рисунок 4 — Фрагмент главной страницы при ширине 390 пикселей]

Проверены размеры 1440×900 и 390×844. В итоговой мобильной версии ширина содержимого документа составила 375 пикселей при viewport390 с полосой прокрутки; горизонтального выхода сцены не осталось. Это проверка двух размеров, а не заявление о тестировании всех браузеров и всех устройств. Системное переключение reduced motion в ходе ручного прогона не эмулировалось; соответствующие ветви проверены по реализации.

## 3.3 Административное SPA и ИИ

Раздел обзора получает статистику backend и показывает число складских заказов, выручку по выданным заказам, число реальных моделей и предложений. Комплектующие и предложения имеют формы создания и изменения. Цена вводится в тенге, характеристики компонента — JSON объектом, ссылка предложения должна использовать HTTPS.

Заказы показывают сохранённые цены позиций, а не текущую стоимость каталога. Форма статуса предлагает только допустимые следующие состояния. Окончательную проверку выполняет OrderService. Пользователи представлены таблицей с выбором роли; сервер запрещает опасное удаление последнего администратора через понижение его роли. Эти операции относятся к учебной системе KeyCraft, а не к кабинетам магазинов.

[FIGURE admin-overview.jpg | Рисунок 5 — Обзор административного SPA после учебного наполнения]

ИИ-помощник отправляет бюджет и пожелания в retail/recommendations. Сервер передаёт модели только допустимый каталог и текст задачи, без email, пользовательского токена и идентификатора аккаунта. Для текущего стенда используется Groq. OpenAI поддерживается отдельно, но автоматическая подмена провайдера отсутствует.

Модель возвращает три ID и объяснение. Сервер проверяет существование ID, правильность категории, совместимость и итоговую сумму. Бюджет и цены для модели передаются в тенге с явными именами budget_kzt и price_kzt; внутри прикладного API продолжают использоваться тиыны. Текст объяснения не является источником финансового итога: проверенный расчёт выводится отдельно.

[FIGURE ai-expanded.jpg | Рисунок 6 — Реальный ИИ-подбор новых деталей за 78717 тенге]

В расширенном каталоге модель выбрала GMMK 2 65% Black, HyperX Linear Red и GPBT Black Ash. Сервер подтвердил 78 717 ₸ при бюджете 90 000 ₸. Первый запрос получил 503 из-за отказа Groq с HTTP 400; повторный запрос завершился успешно. Подбор можно перенести в конструктор и изменить. Результат не создаёт заказ, не гарантирует субъективное ощущение тишины и не бронирует наличие магазина.

# ЗАКЛЮЧЕНИЕ

Я реализовал Frontend KeyCraft AI с публичным сайтом, конструктором реальных комплектующих, личными списками и административным SPA. Выбранный стек соответствует итоговому заданию: Next.js, менеджер состояния React Context API, Tailwind CSS и дополнительные эффекты GSAP. Формы связаны с готовым Laravel backend, а проверка прав выполняется как в интерфейсе, так и на сервере.

Практическая особенность результата — расчёт комплектности реальной покупки. Основа уже содержит часть деталей, свитчи считаются целыми упаковками, а ссылка ведёт на конкретную карточку продавца. В каталоге 20 моделей и 27 предложений; цена и наличие сопровождаются датой проверки. Реальный ИИ использует только доступный каталог и проходит серверную проверку результата.

Проверки подтвердили сохранение черновика, работу авторизации и CRUD, расчёт упаковок, успешный запрос Groq и адаптивность на двух размерах экрана. Серверная часть прошла 73 теста с 469 утверждениями, HTTP-клиент —6 тестов, производственная сборка завершилась успешно. Документация охватывает 44 операции API и остаётся локальной.

Ограничения связаны с объёмом проверенного каталога, обновлением снимка вручную, внешней доступностью ИИ и инструментальными зависимостями разработки. В дальнейшем можно расширить ассортимент, автоматизировать обновление предложений при наличии согласованного API продавцов и добавить проверки на физических мобильных устройствах. Текущая работа готова к локальной демонстрации; оценка и сдача преподавателю в ходе подготовки не выполнялись.

Я открываю главную страницу и демонстрирую разбор клавиатуры. Затем показываю поиск и фильтр Белого Ветра, карточку GPBT Black Ash и прямую ссылку продавца. В конструкторе выбираю Lynx 36 и объясняю округление до трёх упаковок. После входа сохраняю сборку и открываю её из личного кабинета.

Для запуска подготовлены README и Start-KeyCraft.ps1. Сначала устанавливаются зависимости Composer и npm, настраивается .env, выполняются миграции и сборка Next.js. MySQL должен быть запущен отдельно; на текущем компьютере предусмотрена отдельная локальная команда запуска учебной базы.
